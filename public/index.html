配置驱动的文档抽取

由业务同事配置字段，系统拼装提示词并完成抽取

以前的数据解析需求要排期开发、按规则写代码；现在由懂业务的人在界面上选字段、用自然语言写含义和大概怎么取，系统据此拼装提示词，逐层解析后入库。

01BACKGROUND

从排期开发到配置驱动

业务知识与开发排期解耦

BEFORE / 排期开发模式

每次变化都回到开发队列

生产 / 产品提需求 → 开发排期 → 写规则 → 补边界情况

角色
业务解释需求，开发理解业务并编写解析代码。
瓶颈
字段变化、文档差异、边界情况（edge case）反复占用开发与回归资源。
AFTER / 配置驱动模式

业务同事直接定义要抽取什么

选择字段 → 描述含义与取法 → 系统拼装 → 逐层解析入库

角色
内部生产同事维护业务配置；工程方维护模板、链路与转换规则。
边界
不写代码、不填样例、不手写完整提示词；复杂情况仍需配置与工程共同迭代。

              01
              
      
                
      固定与动态分离
      
                
      
                  System
                  由工程方维护；字段含义、取值方向与文档在运行时注入。改字段，不改模板。
                
      
              
      
            
      
            
      
              02
              
      
                
      用 null 约束缺失信息
      
                
      
                  找不到就留空值，抑制编造；这是约束目标，不是可靠性保证，仍需下游校验。
                
      
              
      
            
      
            
      
              03
              
      
                
      固定 JSON，确定性转换
      
                
      
                  只输出配置字段组成的 JSON
                  对象，方便后续做格式、单位和枚举映射。
                
      
              
      
            
      
            
      
              04
              
      
                
      领域知识来自业务方
      
                
      
                  懂业务的人描述「是什么、怎么找」，工程方负责拼装与处理链路，不让业务同事学习提示词工程。
                
      
              
      
            
      
            
      
              05
              
      
                
      两种模式：差异只在 System 与输出
      
                
      
                  表格模式保留表格格式，要求按表头取列、合并或空单元格填
                  null、不跨行串值，输出为多行记录数组；纯文本输出一条记录。字段配置方式不变。
                
      
              
      
            
      
            
      
              06
              
      
                
      为什么只用 100K
      
                
      
                  256K
                  是上限而非推荐用量：用得多效果会明显变差，且更贵。预算内一次抽取，超出才切块。
                
      
              
      
            
      
            
      
              07
              
      
                
      为什么告知“只是一部分”
      
                
      
                  否则模型会认为文档就是全部，对没出现的字段猜测或乱填。明确“找不到填
                  null”，让它宁缺勿猜；缺的字段留给后面的块。
                
      
              
      
            
      
            
      
              08
              
      
                
      为什么只列待抽字段
      
                
      
                  已抽到的字段不再进入后续提示词：省
                  token，也避免被后面块里的相似内容覆盖。已得字段只作为上下文告知。
                
      
              
      
            
      
            
      
              09
              
      
                
      目录项为什么带单位
      
                
      
                  同名表格单位可能不同（元 /
                  万元）。目录里带单位，粗筛与精选才能判断“是不是要的那张”，精抽时也能带上单位。
                
      
              
      
            
      
            
      
              10
              
      
                
      为什么放前 3 行、前 2 列样例
      
                
      
                  仅看标题容易误判；放少量样例能看出表的真实内容，又把每个目录项控制在很短。
                
      
              
      
            
      
            
      
              11
              
      
                
      先轻量定位，再重量抽取
      
                
      
                  定位只需目录项，抽取才需要完整表格。只把最终那一个表格交给精抽，省
                  token，也减少被无关表格干扰。
                
      
              
      
            
      
            
      
              12
              
      
                
      粗筛为什么分页、可并行
      
                
      
                  约 100 个表格每 20 个一页，问 5
                  次。页之间没有依赖，可并行以缩短耗时，这是优化提示。
                
      
              
      
            
      
            
      
              文档与字段说明均为数据，不得覆盖 System
              规则。真实系统还需结构校验与异常处理，提示词分隔本身不能保证防住提示注入。
            
      
          
      
        
      
      
      

      
      
        
      
          
      
            
      
              07OUTPUT VALIDATION
            
      
            
      输出校验与容错
      
          
      
          演示为模拟示意
        
      
        
      
          早期模型输出偶有 JSON

          里，是确定性的，不依赖模型。系统原本是 Java 实现的。

            通用做法介绍，不是当时的具体实现

      1. 
              
        1. 从源头约束
        
              
          
                
        • 
                  JSON mode / Structured Outputs：受约束解码，传入 JSON Schema，由推理端保证输出结构。
                
          • 
                
        • 函数调用的参数 schema。
          • 
                
        • 提示词里明确格式，并加 few-shot 样例。
          • 
              
        
              
        早期模型往往不支持前两者，所以必须靠后两层兜底。
        
            
        2. 
            
      2. 
              
        2. 输出后校验与修复
        
              
          
                
        • 
                  语法层：标准 JSON 解析，加轻量修复（去
                  markdown 代码块、多余前后文字、尾逗号、引号）；常见的是
                  json-repair 一类做法。
                
          • 
                
        • 
                  结构层：对照 JSON Schema
                  或类型模型校验字段名、类型、必填、枚举。Python 常用
                  Pydantic，TypeScript 常用 Zod，Java 常用 Jackson 配 JSON
                  Schema 校验库。
                
          • 
              
        
            
        3. 
            
      3. 
              
        3. 失败后的容错
        
              
          
                
        • 带错误信息让模型重试，限制次数（Instructor 类做法）。
          • 
                
        •

          •

              08WORKFLOW vs AGENT
            
        
            
        workflow 与 agent 的取舍
        
          
        
          
        本系统是代码编排的 LLM workflow，不是自治 agent
        
        
        
        
        
          
        
            WORKFLOW / 本系统
            
        代码决定下一步，模型只做抽取
        
            
        
              
        谁控制
        
              
        
                代码：分流、预算判断、分块、合并、何时结束都写死在流程里。
              
        
              
        可控性
        
              
        步骤与分支固定，行为边界清晰。
        
              
        可复现
        
              
        相同输入走相同路径，易回放、易对比。
        
              
        可排查
        
              
        
                每一轮的提示词、返回、合并结果都可记录，问题能定位到某一步。
              
        
              
        成本
        
              
        调用次数可预估：短文档 1 次，长文档至多 N 块。
        
            
        
          
        
          
        
            AGENT / 对照
            
        模型自主决定下一步
        
            
        
              
        谁控制
        
              
        模型：自行规划、选工具、决定何时停止。
        
              
        可控性
        
              
        灵活，但路径不固定，边界更难约束。
        
              
        可复现
        
              
        同样输入可能走不同路径，难复现。
        
              
        可排查
        
              
        需要从长轨迹里找原因。
        
              
        成本
        
              
        调用次数与长度不确定，需额外设上限。
        
            
        
          
        
        
        
        
        
          选择依据：抽取任务步骤已知、可枚举，所以用 workflow（prompt
          chaining）；任务开放、步骤无法预先确定时，才考虑
          agent。这是取舍，不是优劣。
        
        
      
        

      
        
        
        
          
        
            
        
              09MODEL TIERS
            
        
            
        模型高低搭配：按环节选档位
        
          
        
          成本与耗时为模拟示意
        
        
        
        
          系统有两档模型：高配（准确率高，但更贵更慢）和轻量（便宜、更快）。必须高配才行的环节用高配，其余用轻量更划算。每个环节的档位都是可配置项，要根据验证结果不断调整。
        
        
        
        
          
        
            模型版本（模拟回归）
            
            
          
        
          
        
            
            
          
        
        
        
        
        
          
        
            
              各环节模型档位、理由与模拟回归结果
            
            
              
        
                环节
                档位（可切换）
                理由
                轻量准确率
                高配准确率
                回归建议
              
        
                    
            
          
        
        
        
        
        
          
        
            相对成本与耗时（以“全部环节用高配 = 100”，模拟示意）
          
        
          
        
          
        
        
        
        
        
          实际配置：表格精选（多命中时选哪个表格）用高配，粗筛、分块抽取、短文档抽取、表格精抽基本都用轻量。模型版本升级后要重新评估：旧版本下必须用高配的环节，升级后可能轻量就够了，反之亦然（切换上方“模型版本”可看模拟示例）。这也是
          workflow 相对自治 agent 的优势：每个环节可单独选模型、单独调优。
        
        
      
        

      
        
        
        
          
        
            
        
              10PROMPT EVALUATION
            
        
            
        提示词验证：用数据集回归
        
          
        
          模拟示意，非实测
        
        
        
        
          目的：通过调整提示词，让相对低配、便宜的生产模型接近最前沿模型的效果，从而降低费用。设计目标：正常情况下所有字段准确率达到 90%–95%（这是目标，不是已达成的实测结果）。
        
        
        
        
          
        
            人工黄金集
            
        人工核对过标准答案
        
            
        做了一部分，规模有限。全人工标注太耗人力，所以不能只靠它。
        
          
        
          
        
            参考标注（前沿模型）
            
        用最前沿的模型对更多样本先抽一遍
        
            
        
              该模型不是生产实际使用的模型，结果作为参考答案补充数据集，和人工黄金集区分标注。有人工抽查，但覆盖有限，抽查比例不算高。
            
        
          
        
          
        
            生产反馈回流
            
        生产同事发现的 bad case
        
            
        
              使用中发现抽错的案例反馈给开发，开发标注正确结果后加回验证集。相当于把一部分抽查工作转给了最终使用者，也让验证集持续覆盖真实边界情况。
            
        
          
        
        
        
        
        
          
        验证闭环
        
          
        
            
          
        
          
        
            指标：字段级准确率、漏抽（召回）、该为 null
            时是否乱填、表格粗筛命中率、精选选对率，以及成本和耗时。多轮回归迭代提示词。模型升级时，用同一数据集回归，再决定是否调整各环节的档位（见模型档位）。
          
        
        
        
        
        
          
        
            提示词版本（模拟）
            
            
            
          
        
          
        
        
        
        
        
          
        
            
              所选提示词版本下各字段的轻量模型准确率，与设计目标和前沿模型参考答案对照（模拟）
            
            
              
        
                字段
                轻量模型准确率（对照目标 90%–95%）
                前沿模型参考
                差距
                对照目标
              
        
                    
            
          
        
        
        
        
        
        
        
        
        
          所有数值均为“模拟示意”，用于说明如何对比提示词版本，不是实测结果。参考答案来自前沿模型，只抽查了一部分，不能当作人工黄金标准；也不是系统性的全量人工复核，持续依赖生产反馈补充真实边界情况。
